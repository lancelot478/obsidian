## 服务端安装指南

> Token: CtQAdt1NLoAjGFxmRoxc5LI0nPe

### 1. 工具安装

| 分类 | 内容 |
|------|------|
| **Git客户端** | Fork客户端 windows/macOS: https://git-fork.com/ |
| | 【windows必要】安装完Fork，需要Fork自带的Git命令行工具添加到系统的路径中 |
| **Git仓库地址** | 1. 服务端代码仓库：`git@git.xindong.com:ttdbl3/server/ttdbl3_server.git` |
| | 2. 导表工具仓库：`git@git.xindong.com:ttdbl3/ttdbl3_exporter.git` |
| | 3. 前后端协议仓库：`git@git.xindong.com:ttdbl3/ttdbl3_proto.git` |
| **Golang安装** | 版本：**go1.24.13** |
| | Windows amd64：https://go.dev/dl/go1.24.13.windows-amd64.msi |
| | macOS amd64(intel芯片)：https://go.dev/dl/go1.24.13.darwin-amd64.pkg |
| | macOS arm64(Apple芯片)：https://go.dev/dl/go1.24.13.darwin-arm64.pkg |
| **辅助工具** | **Windows**: |
| | 1. 打开`PowerShell`，或安装使用 `Windows Terminal` |
| | 2. 执行：`Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser` |
| | 3. 执行：`Invoke-RestMethod -Uri https://get.scoop.sh | Invoke-Expression` |
| | 4. `scoop install busybox`（make的执行环境） |
| | 5. `scoop install make`（服务器） |
| | 6. `scoop install redis`（数据库） |
| | **macOS**: |
| | 1. 安装 `homebrew`：https://brew.sh/ |
| | 2. `brew install redis`（数据库） |
| **服务器编译** | 编译必要的服务器程序: `make zagent zbroker zmaster zlogin zgame zbattle` |
| | 或一键编译：`make localserver` |
| **服务器运行** | 1. 启动 `Redis` 数据库: |
| | - linux/macOS：`nohup redis-server --port 13000 --protected-mode no &` |
| | - windows：`Start-Process -FilePath "redis-server" -ArgumentList "--port 13000 --protected-mode no" -WindowStyle Hidden` |
| | 2. 创建必要的目录：`make -p run` |
| | 3. 分别启动服务器（agent/broker/master/login/game/battle/gmops/platform） |
| | 或一键启动：`./scripts/localserver-admin.ps1 start` |
| **服务器地址** | 暴露给客户端的连接端口：9000 |

## 服务端SpecKit

> Token: AMOBdKdjPoEukyxrsjdcBFnlnee
> 官网：https://speckit.org/

### 安装Speckit

| 分类 | 内容 |
|------|------|
| **前置工具** | 安装 `uv` |
| | - Windows：`powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"` |
| | - macOS：`brew install uv` |
| **安装Speckit** | `uv tool install specify-cli --from git+https://github.com/github/spec-kit.git` |

### 安装到项目中

1. 在项目根目录执行：`specify init .`
2. 依据实际情况选择AI助手工具（当前选择 `cursor-agent`）
3. 选择脚本类型（Windows下选择PowerShell，macOS/Linux下选择Bash）
4. 对于非Git工程（如使用P4的客户端工程）：`specify init . --no-git`

### 基本工作流

在Cursor的Agent输入框执行：`/specify → /clarify → /plan → /checklist → /tasks → /analyze → /implement`

| 步骤 | Speckit指令 | 说明 |
|------|-------------|------|
| 1（必要） | `/speckit.constitution` | 制定整个工作流必须遵守的全局原则与约束。输出 `constitution.md` |
| 2（必要） | `/speckit.specify` | 把原始需求转化为标准化、结构化的 spec 文档。输出 `spec.md` |
| 3（按需） | `/speckit.clarify` | 需求澄清，找出spec里的"不确定性" |
| 4（必要） | `/speckit.plan` | 技术设计，把需求转成"可实现的技术方案"。输出 `plan.md`、`data-model.md`、`contracts/` |
| 5（按需） | `/speckit.checklist` | 质量闸门，对spec做工程级质量检查 |
| 6（必要） | `/speckit.tasks` | 任务拆解，将技术方案拆分为可执行的具体开发任务。输出 `tasks.md` |
| 7（按需） | `/speckit.analyze` | 一致性与覆盖校验，确保需求正确落地 |
| 8（必要） | `/speckit.implement` | 实现阶段，根据tasks + plan生成代码 |

### 实际体验要点

- **文档即代码**：只能修改md文档，不能手改业务代码
- 需求文档一定要和策划对清楚，尤其是模糊或不清楚的内容
- 流程比较繁琐，但执行后思考更全面，可有效减少后期返工
- 初次上手需花费一定时间，熟练后随着经验积累和沉淀能提升需求落地效率和质量
- 效率上 AI 生成代码速度显著优于手写的，产出质量比较依赖前期spec、plan阶段的产出

## 服务端OpenSpec

> Token: NeS4dfYxFoImY4xzYfycJ1U3nUg
> 官网：https://openspec.dev/

### 安装OpenSpec

```bash
npm install -g @fission-ai/openspec@latest
```

### 安装到项目中

```bash
openspec init
```
选择 `Cursor` 或 `Codex`

### 扩展安装（必要）

```bash
openspec config profile
```
选择 `Delivery and workflows` → `Both (skills + commands)` → 选择所有 `workflows`

### 基本工作流

#### 基础模式
```
/opsx:propose ──► /opsx:apply ──► /opsx:archive
```

| 步骤 | OpenSpec指令 | 说明 |
|------|--------------|------|
| 1（必要） | `/opsx:propose` | 生成 proposal.md、design.md、specs/**.md、tasks.md |
| 2（必要） | `/opsx:apply` | 生成具体的业务代码 |
| 3（必要） | `/opsx:archive` | 需求归档 |

#### 自定义工作流（推荐）
```
/opsx:new ──► /opsx:continue ──► /opsx:apply ──► /opsx:verify ──► /opsx:archive
```

| 步骤 | OpenSpec指令 | 说明 |
|------|--------------|------|
| 1（必要） | `/opsx:new` | 需求的开始 |
| 2（可选） | `/opsx:explore` | 需求探索 |
| 3-6（必要） | `/opsx:continue` | 依次生成 proposal.md、design.md、specs/**.md、tasks.md |
| 7（必要） | `/opsx:apply` | 生成具体的业务代码 |
| 8（必要） | `/opsx:verify` | 校验需求是否实现完成 |
| 9（必要） | `/opsx:archive` | 需求归档 |

### 特点

- 生成的md文档几乎都包括技术细节，比较适合程序
- 与SpecKit相比更轻量级

## 服务端工作流

> Token: HZZYdMSfZokxRmxuJgmc5Nj3nze

主要制定一套适用于服务端AI工作流的相关规范，Agent工具包括 `Cursor` 或者 `Codex`。

### 一、工作流示例

以`背包系统`为基础，梳理整个工作流：

1. 使用 `openspec` 作为执行引擎，完成需求到实现的全流程
   - 需要自定义openspec工作流
   - 可以独立使用其中部分agent，但要确保统一的spec、plan、tasks等产出

2. 整理实现阶段需要用到的 `SKILL`：
   - 从 `PB协议` 到 `基础接口处理代码` 的生成规范
   - 配置表结构、数据库结构的生成规范
   - 单元测试、接口测试
   - 代码审查
   - 代码合并

3. 在实现阶段（对应于openspec:apply），采用superpowers工作模式

4. 完成一轮需求后，使用知识沉淀相关SKILL归档到项目中
